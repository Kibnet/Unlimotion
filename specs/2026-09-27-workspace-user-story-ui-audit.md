## 1. Overview / Цель

Проверить, может ли человек пройти **каждую** из UX-01–UX-13 от исходной ситуации до предметного результата в текущем нативном приложении. Недостающие сквозные UI-тесты добавить, запустить и по фактам составить список продуктовых и тестовых доработок. Не считать набор разрозненных проверок контролов подтверждением истории.

**Success means:** матрица 13/13 содержит автоматический маршрут или честно обозначенную платформенную границу; каждый сценарий утверждает наблюдаемый итог (файл, существующая задача, статус, контекст/позиция, отсутствие дубля), а отчёт различает `PASS`, дефект продукта, дефект теста/фикстуры и отказ окружения. Числовое «10/10» без маршрутов и evidence не выдаётся.

**Stop rules:** точное «Спеку подтверждаю» получено 29.09.2026; не править продуктовые файлы ради зелёных тестов без отдельной SPEC/согласования. Не считать FlaUI `SendInput: Access denied` дефектом приложения. Не использовать личную базу заметок как fixture.

## 3. Проблема

Сейчас suite подтверждает отдельные механизмы, но не даёт ответа на вопрос пользователя: удобны ли 13 реальных последовательностей и достигается ли в каждой требуемый результат. Падение старых AppAutomation-тестов дополнительно снижает доверие к диагностике UI.

## 4. Цели дизайна

- Один детерминированный синтетический набор с фиксированным «сегодня» и изолированными task/vault каталогами; не менять системное время или боевую базу.
- 13 именованных сценарных проверок на настоящем Avalonia UI, где действие идёт через доступный пользователю контрол. Прямые вызовы ViewModel разрешены только для подготовки fixture и наблюдения сохранённого состояния.
- Сохранять отдельные component/regression тесты и стабильные `AutomationId`; обновить устаревшие маршруты, не подменять новый UX старым mode-switch контрактом.
- После тестов выпускать матрицу с evidence и приоритетными продукт/UX/тест-harness findings, без фиктивного PASS.

## 5. Non-Goals

- Исправлять выявленные продуктовые дефекты, переписывать навигацию, task engine, Markdown/editor или storage в этом цикле.
- Подключать настоящую личную базу, выполнять опасные операции с ней или делать release/PR/push.
- Объявлять HTML-макет либо headless PNG доказательством нативного pointer/OS flow.
- Принудительно запускать FlaUI в сессии, где Win32 запретил ввод; отсутствие доступа не обходить сменой низкоуровневого метода.

### 6.6 Runtime / Config / Data Contract

Тесты не меняют формат пользовательских файлов и config. Fixture создаёт временный vault и task source, удаляет только собственные временные каталоги по явным путям после закрытия session; код cleanup не касается активного профиля. Внешний protocol handler читается/проверяется нативно только в тестовом контексте, без изменения пользовательской регистрации.

## 7. Инварианты

«Пункт заметки» не равен Task; цель — признак Task; срочно = срок сегодня, просрочено = срок раньше сегодня, а «сегодня» — начало сегодня. Доступность по блокерам, статус и время не смешиваются. Одно имя заметки в разных каталогах — два файла; одна Task ID в пределах пространства — один объект. Повторное открытие не создаёт дубликат. Утверждение каждого сценария требует не только наличия кнопки, но и предметного результата.

## 8–10. Интеграция, состояние, rollout

Точки входа: общие `+`, поиск, лента, разбор, настройки, дерево/фильтры задач, ссылки, workspace tab/history/pane, `unlimotion://`. Производственный код и модель данных не меняются. Rollback тестового изменения — откат новых test/helper файлов; существующие tests не удаляются. Если понадобится новый `AutomationId`, сначала подтвердить, что существующий недоступен и что добавление не меняет UX.
