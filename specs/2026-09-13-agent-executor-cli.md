## 1. Обзор / Цель

Сделать `unlimotion-cli` самодостаточным и безопасным интерфейсом для агента-исполнителя, который работает с подготовленными задачами без прямого редактирования файлов: находит кандидата, получает полный контекст, атомарно закрепляет задачу, фиксирует вопросы и результаты, а затем завершает либо освобождает её.

Контракт результата:

- Успех означает:
  - два конкурентных агента не могут оба считать одну Prepared-задачу закреплённой за собой;
  - агент получает через CLI весь контекст, нужный для решения: описание, критерии, связи, историю статусов, состояние исполнения и компактные сведения о соседних задачах;
  - агент может через CLI записать идентификатор, вопросы, ответы, итог и ссылки, не повреждая пользовательский текст описания;
  - формальное завершение и release проверяют тот же lease, что и claim;
  - старые файлы задач и существующие команды CLI остаются совместимыми.
- Итоговый артефакт: расширенный `Unlimotion.Cli`, обновлённая README и контрактные тесты; жизненный цикл агента воспроизводим только командами CLI.
- Правила остановки:
  - не реализовывать пространство задач в серверном режиме, UI desktop-приложения или публикацию пакета;
  - при невалидном графе, конфликте lease, конфликте служебного блока Description либо недоказанном результате записи остановиться с типизированной JSON-ошибкой, ничего не «додумывать» и не повторять запись автоматически;
  - до финального EXEC-отчёта обязательны целевые тесты, сборка затронутого кода и полный успешный запуск TUnit; при невозможности — завершить как заблокированное/неполное с доказательствами.

## 2. Текущее состояние (AS-IS)

- Официальный пакет `Unlimotion.Cli` 1.30.1 установлен глобально и без `--tasks` определяет активное локальное пространство задач через desktop `Settings.json`; метаданные пакета указывают на `v1.30.1` / `0b6e897d`.
- Сейчас CLI предоставляет `status`, `unlocked`, `task`, `validate`, `set-status`, `complete`, `set-criterion`, `satisfy-criterion`.
- `unlocked` выдаёт все `CanStart=true` задачи. В проверенном активном графе это были 830 задач: 14 Prepared, 10 InProgress и 806 NotReady. У CLI нет серверной фильтрации кандидатов, лимита или детерминированной сортировки.
- `task --id` возвращает `TaskAvailabilityAnalysis`: идентификатор, название, статус, флаги доступности и причины. Он не возвращает Description, связи, критерии, историю, владельца, вопросы, результаты или ссылки.
- `set-status` и `complete` используют `TaskGraphCommandService`, предварительную проверку графа, блокировку каталога, атомарную замену и повторное чтение после записи. Однако параллельные `set-status ... InProgress` дают одну запись и один успешный no-op; публичный вывод не сообщает владельца, поэтому no-op не равен успешному claim.
- `TaskItem` уже хранится как JSON и имеет `JsonExtensionData`; `TaskItemSnapshot.Clone` вручную глубоко копирует известные коллекции. Новая сохраняемая модель должна быть явно скопирована и не потеряться при обновлениях через общий движок.
- `TaskDirectoryResolver` читает только нужную проекцию совместимости desktop-приложения, поддерживает явный `--tasks` и типизированные ошибки настроек. Это поведение сохраняется.

## 3. Проблема

Текущий CLI умеет безопасно выполнить отдельный переход статуса, но не выражает протокол владения и исполнения. Агент вынужден смешивать CLI с прямой записью JSON или внешней памятью: он не может доказать, что именно он взял задачу, получить её смысловой контекст или оставить проверяемый итог. Это создаёт гонки, потерю результатов и неконтролируемые обходы общего движка задач.

## 4. Цели дизайна

- Выделить отдельный контракт исполнения, не превращая `Description` в единственный источник истины.
- Сделать claim операцией сравнения-и-установки под существующей блокировкой каталога.
- Сохранить читаемый пользователю след исполнения в Description, но хранить машиночитаемые данные отдельно и без потери произвольного Markdown.
- Сохранить обратную совместимость JSON, старых desktop-клиентов и текущих форм ответов CLI по умолчанию.
- Дать агенту один ограниченный снимок вместо неограниченного обхода всего графа.
- Сделать ошибки, конкуренцию и outcome unknown явными в JSON и удобными для автоматизации.

## 5. Вне цели (чего НЕ делаем)

- Не добавляем серверное пространство задач, сетевую аутентификацию, удалённые блокировки или распределённые lease между разными хранилищами.
- Не меняем UI desktop-приложения, статусы задач и существующие правила доступности. `AwaitingInput` будет состоянием исполнения, а не новым `TaskStatus`.
- Не даём CLI право самостоятельно отправлять сообщения, электронную почту, мессенджеры или запускать внешние инструменты.
- Не реализуем произвольный редактор всех полей и отношений задачи; CLI создаёт follow-up задачу и управляет данными исполнения только в явно определённых командах.
- Не публикуем новый пакет NuGet, релиз или PR в рамках этой SPEC без отдельного разрешения.

### 6.2 Детальный дизайн

#### Сохраняемое состояние исполнения

В `TaskItem` добавить nullable `AgentExecution` с отдельными типами в `Unlimotion.Domain`:

```text
AgentExecutionRecord
  AgentId: string
  LeaseId: string (GUID, создаётся CLI при claim)
  State: Active | AwaitingInput | Released | Completed
  ClaimedAt, UpdatedAt: DateTimeOffset
  Questions: [{ Id, Text, AskedAt, Answer?, AnsweredAt? }]
  Result?: { Summary, Links: [absolute URI], RecordedAt }
  ReleasedAt?, ReleaseReason?
  PreviousAttempts: [{ AgentId, LeaseId, ClaimedAt, ReleasedAt?, ReleaseReason?, CompletedAt? }]
```

- Поле отсутствует у старых задач. Его отсутствие означает «задача не закреплена агентским протоколом».
- `AgentId`, текст вопроса, ответ, итог, причина release и ссылки имеют ограничение длины/количества; пустые, дублирующиеся или невалидные значения отвергаются как `invalidArguments` до записи. Любое значение, которое выводится в зарезервированный блок, не может содержать буквальные start- или end-marker; это также `invalidArguments` до записи, а не неявное экранирование.
- `Links` принимают только абсолютные URI со схемой `http`, `https` или `file`, не загружаются и не исполняются CLI.
- `AgentExecution` — источник истины для машинного контракта. CLI также поддерживает единственный зарезервированный блок Markdown в Description:

```text
<!-- unlimotion-agent-execution:v1:start -->
Исполнитель: <AgentId>
Состояние: <State>
Вопросы: ...
Результат: ...
Ссылки: ...
<!-- unlimotion-agent-execution:v1:end -->
```

  CLI добавляет или заменяет только этот блок. Подстроки Description до start-marker и после end-marker сохраняются посимвольно; когда marker добавляется впервые, прежняя Description остаётся неизменной, кроме однозначно документированного разделяющего перевода строки непосредственно перед новым блоком. Два блока, непарные/повреждённые markers или ручной конфликт с зарезервированным блоком дают `descriptionMarkerConflict` и не выполняют запись.
- Новый property обязан глубоко копироваться в `TaskItemSnapshot`; старый JSON без него сериализуется/десериализуется без миграции. Неизвестные поля расширений продолжают сохраняться.
- Новый claim после `Released` переносит предшествующие данные claim/release в неизменяемый `PreviousAttempts`, затем создаёт новый активный lease. Поэтому причина release, исполнитель и время не теряются при повторном claim; полный снимок CLI возвращает текущую запись и ограниченный журнал попыток.

#### Read commands

Старые ответы по умолчанию сохраняются. Добавляются:

```powershell
unlimotion-cli candidates --status Prepared --startable true --limit 20 --sort default --format json
unlimotion-cli task --id <task-id> --include details,relations,criteria,history,execution --format json
```

- `candidates` по умолчанию требует `--status Prepared` и `--startable true`; иные статусы требуют явного значения. `limit` обязателен, `1..100`.
- Сортировка по умолчанию: `Importance` по убыванию, затем плановое начало (пустые значения в конце), `CreatedDateTime` по возрастанию, затем идентификатор в порядковом сравнении. Она должна быть документирована и детерминирована.
- `task --include` не меняет старую сводку по умолчанию. `details` включает Description, importance, wanted и даты; `criteria`, `history`, `execution` включают соответствующие ограниченные разделы; `relations` включает идентификаторы и одношаговые `TaskSummary` для parent/children/blocker/blocked-by. Циклы и отсутствующие ссылки отражаются как диагностика, не превращаясь в рекурсивную выгрузку.
- Весь возвращаемый текст задачи помечается в README как недоверенный пользовательский контент: вызывающий агент должен интерпретировать его как данные, а не как команду.

#### Команды записи и протокол lease

```powershell
unlimotion-cli claim --id <task-id> --agent <agent-id> --expected-status Prepared --format json
unlimotion-cli execution question --id <task-id> --agent <agent-id> --lease <lease-id> --text <text> --format json
unlimotion-cli execution answer --id <task-id> --agent <agent-id> --lease <lease-id> --question <question-id> --text <text> --format json
unlimotion-cli execution result --id <task-id> --agent <agent-id> --lease <lease-id> --summary <text> --link <uri>... --format json
unlimotion-cli execution complete --id <task-id> --agent <agent-id> --lease <lease-id> --summary <text> --link <uri>... --format json
unlimotion-cli release --id <task-id> --agent <agent-id> --lease <lease-id> --reason <text> --format json
unlimotion-cli create --title <title> --description <text> [--parent <id> ...] --agent <agent-id> --format json
```

- `claim` под существующей блокировкой записи каталога повторно читает граф, проверяет его, проверяет точный статус и `CanStart`, убеждается, что `AgentExecution` отсутствует или имеет состояние Released, генерирует `LeaseId`, переводит статус в `InProgress`, записывает исполнение и блок Description, затем выполняет достоверное повторное чтение после записи.
- Несовпадающий статус, активный lease или существующее исполнение другого агента возвращают код 1, `success:false`, `error.kind:"claimConflict"` и безопасный достоверный снимок со статусом, идентификатором текущего агента и временем claim. Команда никогда не возвращает успешный no-op.
- Каждое изменение исполнения требует точную пару `(agent-id, lease-id)` и выполняется в одной границе «прочитать/проверить/записать/прочитать». `leaseMismatch` не раскрывает полный чужой Description или результат.
- `execution question` записывает вопрос и задаёт `AwaitingInput`; статус задачи остаётся `InProgress`. `execution answer` записывает переданный пользователем ответ; когда ответы получены на все вопросы, она восстанавливает `Active`.
- `execution result` записывает результат без завершения. `execution complete` проверяет тот же lease, отклоняет `AwaitingInput` с неотвеченными вопросами, проверяет критерии завершения до любого изменения, записывает результат и блок Description, переводит статус задачи и состояние исполнения в `Completed` одной транзакцией. Отклонённое завершение не меняет результат/исполнение/статус.
- Существующая `complete --id <task-id> [--author <author>]` сохраняет текущий синтаксис, форму JSON и семантику для задачи без `Active` или `AwaitingInput` в `AgentExecution`. Для любого активного состояния исполнения она возвращает код 1 и `executionStateDenied` без изменений: ею нельзя завершить чужой claim. Команда не создаёт и не получает lease. Полный жизненный цикл агента должен использовать `execution complete`.
- `release` выполняется только явно: при валидном lease и статусе `InProgress` задаёт `Released`, записывает `ReleasedAt` и `ReleaseReason`, добавляет попытку в журнал аудита и переводит задачу обратно в `Prepared`. Автоматического тайм-аута или повторного захвата нет.
- `create` создаёт follow-up задачу в `Prepared`, применяет необязательные parent и обратные `ContainsTasks` только через новую операцию движка задач `TryCreateTaskWithinExistingMutationLockAsync`. До первой записи она проверяет каждого parent и весь итоговый граф, подготавливает изменения дочерней задачи и обратных связей как одну мутацию графа, достоверно проверяет чтением после записи, использует `--agent` как автора и возвращает снимок созданной задачи. Она не изменяет произвольные существующие связи.
- Новые успешные ответы содержат `task`, `execution`, `changedTaskIds`, `storageRevision` и `didMutate`. Новые ошибки сохраняют текущую оболочку и используют стабильные виды: `claimConflict`, `leaseMismatch`, `executionStateDenied`, `descriptionMarkerConflict`, `statusPreconditionFailed`, `validationFailed`, `outcomeUnknown`, `operationFailed`, `invalidArguments` и `notFound`.

#### Конкуренция, безопасность и восстановление

- Claim и все изменения lease выполняются внутри `ITaskGraphWriteLock`; чтение перед проверкой происходит после получения блокировки, а не до неё.
- `TryCreateTaskWithinExistingMutationLockAsync` использует ту же блокировку и транзакцию мутации графа в FileTaskStorage: до замены для всех затронутых файлов задач журналируются исходные образы; открытие хранилища под блокировкой завершает или откатывает прерванную транзакцию до выдачи графа. Ошибка после возможного сохранения возвращает только `outcomeUnknown`; восстановление обязано выдать либо полный граф с дочерней задачей и обратными связями, либо исходный граф, но никогда не постоянную полусвязь.
- `didMutate:false` допустим только для операций чтения; команды записи с невыполненными предусловиями завершаются ошибкой.
- При ошибке ввода-вывода после возможного сохранения вернуть `outcomeUnknown` с `authoritativeTask`, если повторное чтение удалось; автоматически не повторять.
- CLI остаётся только для файлового хранилища. Если активный desktop-источник находится в серверном режиме, сохраняется `settingsUnsupported`; явный `--tasks` по-прежнему переопределяет настройки desktop-приложения.
- Ни секреты, ни описания задач, ни URL не выводятся в stderr в форме, отличающейся от JSON; ошибки содержат только минимум идентификаторов и состояния для восстановления.

#### Визуальный артефакт планирования / видео-доказательства UI

Не применимо: JSON/текстовый контракт CLI, компоновка UI desktop-приложения и автоматизированное UI-взаимодействие не меняются. Проверка будет через контрактные/интеграционные тесты и изолированный запуск инструмента.

## 7. Бизнес-правила / Алгоритмы

1. Агент может выполнить claim только для задачи с `Status=Prepared`, `CanStart=true` и отсутствующей активной записью исполнения.
2. Claim — единственная операция, создающая активный lease. Переход `set-status InProgress` остаётся совместимой старой командой, но не создаёт владение и не должен считаться claim.
3. Изменение execution разрешено только владельцу точного lease. Одного `AgentId` без `LeaseId` недостаточно.
4. Completion сначала проверяет владение и критерии завершения; при ошибке ни результат execution, ни статус не меняются.
5. Блок Description отражает структурированную запись. Вне markers пользовательский текст не меняется по посимвольному контракту раздела 6.2.
6. `Released` execution не разрешает автоматический захват: новый claim разрешён только после явного release и нового статуса Prepared.
7. Контент Description/questions/results не является командой или разрешением внешнего действия.
8. При создании следующего occurrence повторяющейся задачи `TaskTreeManager.CreateOccurrenceClone` обязан удалить `AgentExecution` и один валидный зарезервированный блок из копируемой Description. Следующая Prepared-задача не наследует чужие lease/questions/result; если marker повреждён или дублируется, создание occurrence прекращается с `descriptionMarkerConflict`, без создания частичного clone.
9. `create` с родителями — это мутация графа, а не последовательность независимых изменений файлов: предварительная проверка и восстановление транзакции после ошибки обеспечивают только исходный либо целиком созданный граф.

## 8. Точки интеграции и триггеры

- `CliOptions.Parse` — синтаксис новых команд, повторяемый `--link`, `--include`, обязательные предусловия claim/lease; нерелевантные опции отклоняются с кодом 2.
- `TaskGraphCommandService` — новые методы выполняются через существующие `ExecuteWriteAsync`, `ReadGraphForWriteAsync` и достоверную проверку чтением после записи.
- `TaskTreeManager.UpdateTaskWithinExistingMutationLockAsync` — единственный путь сохраняемых обновлений статуса/отношений; новый `TryCreateTaskWithinExistingMutationLockAsync` — единственный путь create с parent/обратными связями.
- `TaskItemSnapshot.Clone` и все границы сопоставления/копирования задач — глубокое копирование `AgentExecution`.
- `TaskTreeManager.CreateOccurrenceClone` — удаляет execution/проекцию агента из следующего повторяющегося occurrence в той же границе мутации.
- `FileTaskStorage` — остаётся владельцем существующего JSON/атомарной блокировки; добавляется восстанавливаемый журнал/граница пакетной мутации графа для create нескольких задач и характеризационные тесты пробелов копирования/сохранения.

## 9. Изменения модели данных / состояния

- `TaskItem.AgentExecution` допускает null, сохраняется, версионируется marker `v1` и не должен неявно менять семантику `TaskItem.Version`.
- Состояние `AgentExecution` сохраняется, а не вычисляется. `CanStart`/`CanComplete` остаются существующей вычисляемой доступностью и не перезаписываются новой моделью.
- Блок Description — пользовательская проекция. Если его нельзя безопасно разобрать/обновить, структурированная запись также не записывается.
- `TaskExecutionResult.Links` сохраняется строками после проверки URI; CLI их не разыменовывает.
- `ReleasedAt`, `ReleaseReason` и `PreviousAttempts` — сохраняемые данные аудита. При следующем claim можно заменить только текущую запись `Released`, а её идентификатор/причина/временные метки сохраняются в ограниченной истории.
- Клон повторителя — новый контекст исполнения: он не сохраняет ни `AgentExecution`, ни её производный marker.

## 10. Миграция / внедрение / откат

- Первое чтение старой задачи: без изменений и `execution:null`.
- Первый claim атомарно создаёт необязательное поле и один зарезервированный блок Description.
- Если завершение с lease создаёт следующий occurrence повторяющейся задачи, новый occurrence сохраняется как чистый контекст execution: без `AgentExecution` и без marker агента в Description.
- Старые desktop-сборки с файловым хранилищем должны сохранять неизвестную `AgentExecution` через текущее поведение расширяемых данных; совместимость доказывается сценарием старой формы, открытым/сохранённым текущим хранилищем, и сценарием текущей формы, сохраняющим нераспознанные данные.
- Прерванный create нескольких задач восстанавливается из журнала мутации графа FileTaskStorage при удержании блокировки каталога. Восстановление проверяет граф и выдаёт исходную либо целиком подтверждённую мутацию; ручное удаление журнала не является рабочим процессом агента.
- Откат кода: совместимый прежний CLI игнорирует необязательное поле; он не может безопасно работать с протоколом lease, поэтому для закреплённых задач оператор обязан использовать новый CLI. Автоматического удаления записей execution нет.
- Откат данных: `release` — поддерживаемое операционное восстановление; ручное исправление файла задачи явно вне обычного процесса агента и требует отдельно разрешённой процедуры восстановления графа.

## 11. Тестирование и критерии приёмки

### Критерии приёмки

- AC-1: `candidates` возвращает только Prepared/startable задачи, никогда InProgress/NotReady, соблюдает лимит `1..100` и детерминированную сортировку.
- AC-2: два конкурентных вызова `claim` создают ровно один сохраняемый переход lease/истории статуса; проигравший получает код 1 `claimConflict`, а не успешный no-op.
- AC-3: полный снимок задачи содержит описание, критерии, одношаговые сводки связей, историю и `execution`; ответ `task` по умолчанию остаётся неизменным.
- AC-4: каждое изменение вопроса/ответа/результата execution требует совпадающих агента и lease; неверный/отсутствующий lease не меняет файл.
- AC-5: `execution complete` с совпадающим lease атомарно записывает результат/ссылки/блок Description и Completed; невыполненные критерии, неотвеченные вопросы или ошибочное предусловие ничего не меняют. Старая `complete` сохраняет синтаксис, форму JSON и семантику для задач без активного execution, но возвращает `executionStateDenied` без изменений при активном/ожидающем lease.
- AC-6: release сохраняет `ReleasedAt`, причину и аудит предыдущей попытки, возвращает только принадлежащую агенту задачу InProgress в Prepared, а повторный claim сохраняет прошлый аудит; автоматического захвата/истечения срока нет.
- AC-7: старый JSON и несвязанные поля расширений переживают все новые записи; повреждённые/дублирующиеся markers и инъекция marker через любое выводимое поле отклоняются до записи.
- AC-8: определение настроек, существующие команды, старые оболочки JSON-успеха/ошибки и семантика статусов сохраняют совместимость.
- AC-9: create возвращает Prepared follow-up и точные обратные связи parent в одной восстанавливаемой транзакции графа; невалидный parent/граф завершается до записи, а внедрённая ошибка во время фиксации нескольких файлов восстанавливается до полностью старого либо полностью нового графа.
- AC-11: завершение повторяющейся задачи создаёт чистый следующий occurrence без `AgentExecution` и marker агента, а завершённый occurrence сохраняет собственные аудит/результат.
- AC-10: README документирует синтаксис команд, границу доверия, JSON-схему/виды ошибок, локальную область и полный процесс агента.

## 12. Риски и граничные случаи

- Desktop-приложение может изменить Description, пока CLI записывает marker. Мера: блокировка + свежее чтение, один зарезервированный блок, ошибка конфликта вместо перезаписи.
- Процесс CLI может аварийно завершиться после сохранения на диск, но до ответа. Мера: `outcomeUnknown` с достоверным обновлением; вызывающая сторона повторно читает и никогда не повторяет запись вслепую.
- Агент может бросить lease. Мера: без небезопасного истечения срока; явный release/восстановление сохраняет журнал аудита.
- Старые клиенты могут не отображать `AgentExecution`. Мера: необязательный JSON, проекция Description и сценарии совместимости.
- Большой граф может замедлить широкий выбор. Мера: ограниченный вывод candidates и отсутствие рекурсивного обхода контекста; во время EXEC измерить сценарий на текущем графе.

## 18. Альтернативы и компромиссы

- Вариант: хранить всё только в Description.
  - Плюсы: нет нового поля предметной области.
  - Минусы: нельзя надёжно сравнивать владельца/lease, разрешать конфликты и выдавать типизированный снимок; легко повредить пользовательский Markdown.
- Вариант: отдельное execution JSON рядом с каждой задачей.
  - Плюсы: изолирует данные агента.
  - Минусы: усложняет атомарность, резервное копирование/синхронизацию и жизненный цикл файлов задач.
- Выбран: необязательный `TaskItem.AgentExecution` плюс зарезервированная проекция Description.
  - Плюсы: одна атомарная запись, структурированный API, читаемый результат, обратная совместимость.
  - Минусы: модель предметной области расширяется и требует покрытия копирования/сопоставления.
  - Почему выбранное решение лучше: оно единственное одновременно закрывает гонку владения, полный контекст, происхождение результата и правило пользователя «исполнитель и итог в описании».
