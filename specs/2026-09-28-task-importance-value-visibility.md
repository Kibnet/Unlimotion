### Визуальный ориентир

```text
Исходный кадр:  Важное [   | ▲ | ▼ ]  ID   (крупные кнопки рядом, область числа пустая)
Цель:           Важное [  9 | ▲ ]     ID   (компактные кнопки одна над другой)
                         [    | ▼ ]
Край:           Важное [100 | ▲ ]     ID   (100 не обрезано)
                         [    | ▼ ]
Узкая карточка: элементы строки могут перенестись; число и обе кнопки остаются видимыми.
```

Это схема ожидаемого состояния, не точный макет и не снимок исправленного UI. Сопоставимый PNG после EXEC должен показывать то же поле, ввод `9`/`100`, вертикальное расположение кнопок и соседние элементы.

### Визуальная регрессия через Headless

Тест открывает настоящую карточку `MainControl` с ресурсами и стилями приложения, находит `CurrentTaskImportanceInput` и получает rendered PNG через существующий Headless. Если bootstrap ещё семантический, настроить тестовый builder через `.UseSkia()` и `.UseHeadless(new AvaloniaHeadlessPlatformOptions { UseHeadlessDrawing = false })`, сохранив необходимые настройки приложения. Из полного кадра выделить область компонента по его фактическим границам и render scale. Не рисовать отдельную имитацию контрола; crop не должен обрезать текст, границу или кнопки.

| Условие | Зафиксированное значение / проверка |
| --- | --- |
| Importance | `0`, `9`, `100`, полученные настоящим вводом; после ухода фокуса и завершения layout/render |
| Шрифт приложения | `12` и `24` через обычную настройку приложения и связанные ресурсы; `24` — поддерживаемый максимум. Не ограничиваться присваиванием `FontSize` тестовому контейнеру |
| Размер окна | Узкий `360 × 844` DIP и обычный `1400 × 900` DIP по существующим сценариям карточки; фактический размер компонента фиксируется отдельно |
| Тема и язык | Light/Dark и русский язык; отдельный эталон для каждого сочетания |
| Рендеринг | Windows, как в текущем `.github/workflows/tests.yml`, render scale `1.0` (100%), SDK по `global.json`; закрепить версии renderer, набор шрифтов и font fallback. Метаданные фактической среды сохранить рядом с эталонами; другая среда не сравнивается с ними как эквивалентная |
| Состояние | Детерминированная задача и положение указателя; убрать фокус с поля, исключить caret, selection, tooltip и незавершённые анимации; дождаться кадра после изменения |

Матрица содержит 24 состояния: `3 значения × 2 шрифта × 2 размера окна × 2 темы`. Это визуальные проверки; полный autosave/reload-сценарий не нужно дублировать для каждого снимка. Для AC4 дополнительно сохранить и открыть полный кадр карточки в обоих размерах: crop одного контрола не доказывает отсутствие перекрытия соседей.

Эталонные PNG и метаданные хранить в `Baselines/TaskImportance/` выбранного UI-тестового проекта, включать в review diff и копировать в output. При первом создании открыть каждый эталон и проверить читаемость числа и целевую вертикальную компоновку; снимок исходного дефекта не становится целевым эталоном. Обновление выполнять отдельным явным действием с просмотром diff; обычный прогон и CI не создают и не перезаписывают эталоны. Отсутствующий эталон, другая геометрия или невозможность получить пиксели означают failure, а не автоматическое принятие нового изображения.

Сравнивать размеры и декодированные пиксели, не PNG-байты или hash файла. В закреплённой среде начать с точного сравнения. Если воспроизводимое отличие сглаживания требует допуска, обосновать и записать его до принятия эталонов; нельзя маскировать числовую область или кнопки либо выбирать общий процент расхождения, скрывающий пропавшую цифру. Обязательны два негативных контрольных изображения: исчезнувшая `9` и горизонтальное расположение кнопок. Сравнение должно отвергать оба. При расхождении сохранять `expected.png`, `actual.png`, `diff.png`, условие матрицы и метаданные рендеринга в `artifacts/task-importance/<run>/<case>/`; сообщение теста содержит абсолютные пути.

### Поведенческая регрессия и проверки EXEC

В изолированном временном task space открыть карточку, ввести `9` через UI, перевести фокус, дождаться autosave и прочитать JSON задачи. Убедиться, что `Importance` равен `9`; затем заново загрузить задачу из storage в новой VM/repository fixture и повторно открыть карточку. Число должно оставаться видимым и равным `9`. Простое присваивание `NumericUpDown.Value`, переключение карточки в той же VM или принудительный save helper не заменяют этот сценарий.

Отдельно проверить увеличение/уменьшение мышью и клавишами, фактический текущий шаг, невозможность выйти за `0..100`, ручной ввод граничных значений, фокус и доступное имя. Assertions VM/JSON и screenshot comparison дополняют друг друга. При этом сохраняются существующие тесты `WantedImportanceUiContract` и карточки; локальное изменение контрола не должно менять Wanted, Title, Status, связи и остальные NumericUpDown.

До UI-fix получить failing regression/characterization на исходном контроле, затем повторить его после исправления. Целевые проверки: новый visual/persistence сценарий, `TaskImportanceUiTests`, `StormTaskPlanningWantedImportanceExecutableSpecTests` и `MainControlTaskCardLayoutUiTests`. Для текущего TUnit/Microsoft.Testing.Platform использовать, например, `dotnet run --project src/Unlimotion.Test/Unlimotion.Test.csproj -- --treenode-filter "/*/*/MainControlTaskCardLayoutUiTests/*"`; новый сценарий запускать по фактическому имени класса в выбранном проекте, а не считать его уже существующим.

После целевых проверок выполнить `dotnet build src/Unlimotion.Desktop/Unlimotion.Desktop.csproj`, сборку выбранного UI-тестового проекта и `dotnet test --project src/Unlimotion.Test/Unlimotion.Test.csproj`. Если используется отдельный `tests/Unlimotion.UiTests.Headless` — дополнительно запустить его релевантные сценарии. Это запланированные команды, не evidence прошедших тестов. Для локального контрола достаточно этого набора, просмотра всех эталонов и кадров до/после; изменение общего test bootstrap требует также regression существующих сценариев затронутого runner. Объективную причину отсутствия video evidence и next-best evidence фиксировать по профилю `ui-automation-testing`.
