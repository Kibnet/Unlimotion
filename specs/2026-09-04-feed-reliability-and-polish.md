## 1. Overview / Цель
Довести существующую ленту до состояния, которому можно доверять ежедневные мысли: записал → продолжил редактировать → разобрал → нашёл позже. Сохранить свободный Markdown, хронологию, тематические области и отсутствие лишних форм.

Outcome contract:
- Success means: закрыты дефекты аудита и AC01–AC14 ниже; нет потерь текста, дубликатов от повтора, неясных частичных операций и сломанных оконных проверок.
- Итоговый артефакт / output: локальный проверенный код, регрессионные тесты, обновлённый журнал этой спеки, честный итоговый отчёт с визуальными доказательствами.
- «10/10» — направление качества, не заранее объявленная оценка. При незакрытом дефекте или непройденной обязательной проверке результат не объявляется готовым.
- Stop rules: SPEC заканчивается запросом approval; EXEC — только после full green, ручной проверки сценариев и post-EXEC review либо с явным blocker/неполным результатом. Новая платформенная возможность, опасная миграция или правка внешней зависимости вне репозитория требует отдельного решения.

## 3. Проблема
Система ещё не сохраняет ощущение непрерывного и безопасного текстового пространства при переходах между редактированием, организацией и преобразованием записи; ошибки и пробелы оконного тестирования не позволяют доверять завершённости операций.

## 4. Цели дизайна
- Уверенность важнее декоративной новизны; свободное редактирование остаётся основным действием.
- Переиспользовать существующие журналы, область-каталог, recovery и блок родителей задачи; не строить параллельную систему.
- UI-поток отвечает за UI-состояние, I/O не блокирует окно.
- Мутации проверяют ревизию и идентичность выбранного текста; внешние изменения никогда не перетираются ради автоматического успеха.
- Одинаковые области, ошибки и действия выглядят одинаково во всех частях ленты.

## 5. Non-Goals (чего НЕ делаем)
- Не переписываем редактор с нуля, не внедряем web-editor, CRDT, новый формат Markdown или новую базу данных.
- Не добавляем глобальную историю Undo для всего приложения, полноценную систему совместного редактирования, мастер миграции файлов или новые окна управления.
- Не переименовываем существующие заметки автоматически; не меняем смысл задачи/цели и контракт родителей.
- Не меняем поведение прочих режимов, кроме общей оболочки/поиска и необходимой совместимости UI.
- Не обещаем OS-global горячие клавиши вне активного приложения, паритет всех мобильных платформ или синхронизацию с живой внешней базой.
- Не удаляем пользовательские данные/артефакты, не коммитим, не пушим, не ребейзим, не публикуем и не обновляем зависимости произвольно.

## 6. Предлагаемое решение (TO-BE)
### 6.1 Распределение ответственности
- `Unlimotion.Notes/Operations/*`: безопасные изменения Markdown, стабильная идентичность операций, повтор/восстановление, условная обратная операция переноса.
- `TaskStorageFeedTaskCreationTarget`: создание/поиск одной задачи, проверка владения operation ID, корректная публикация результата в UI-кэш.
- `FeedViewModel` и recovery VM: согласование текущих ревизий, статусов, фильтров и выбранных областей; одна операция на источник в момент времени.
- Модель Live Preview: выбранные блоки, порядок, merge/split, отображение Markdown; view: visual caret X, focus, input routing, hover и DnD.
- Views оболочки/поиска/настроек: компактная раскладка, понятные сообщения, корректная клавиатура/accessibility.
- Существующий AppAutomation host и тестовые проекты: запуск текущего кода в изолированных данных; диагностика каждого этапа.

### 6.2 Детальный дизайн
#### A. Быстрая задача и восстановление
1. Сохранить существующий capture-first поток и выбор обычной записи/задачи без ручного Markdown. До первой записи закрепить operation ID, vault/space, исходный capture и его безопасный locator диапазона; повтор использует тот же ID, а не заново дописывает текст. Многоабзацный capture/список — один введённый диапазон: преобразуется весь пользовательский ввод, а не последний совпавший блок. Заголовок области, автоматически добавленный вокруг capture, в диапазон замены не входит. Заголовок/описание задачи формируются по существующим правилам преобразования, без потери остального текста.
   Durable intent обязательно атомарно записывается ДО append: operation ID, immutable vault/space/date/source path, исходная revision, payload и ожидаемая идентичность результата append. После crash между append и записью следующей стадии recovery проверяет результат по сохранённому intent. Доказанный результат не дописывается повторно; доказанно отсутствующий можно дописать по исходной revision; неоднозначный/изменённый результат требует безопасного recovery без blind append. Дата фиксируется при первом submit и не меняется при переходе через полночь.
2. Пока выполняется операция, повторная отправка недоступна. Созданная задача и ссылка считаются успешным результатом только после подтверждения обоих сохранений и публикации UI.
3. Между двумя хранилищами нет физической общей транзакции. Гарантия — одна логическая операция с устойчивым журналом, отсутствием потерь и дубликатов и безопасным продолжением после перезапуска.
4. Если задача уже создана, показать «Задача создана, но ссылка ещё не добавлена» с «Завершить» и «Оставить как есть». Второе сохраняет обе сущности и явно завершает recovery без удаления задачи. До первого submit черновик сохраняется в текущей сессии при закрытии формы; после append исходный текст уже сохранён в Markdown и доступен после restart. Новая система постоянных черновиков не вводится; Esc не изображает откат уже записанных данных.
5. Успешное recovery немедленно убирает предупреждение и обновляет ленту без перезапуска. Capture не требует review-session; отметка применения review нужна только операции, которая была создана в разборе.
6. Обработка UI-кэша через dispatcher/репозиторный контракт; никаких `.Result`/`.Wait` на UI. Старый callback после смены пространства не публикуется в новое пространство.
7. Ошибки локализованы существующим механизмом. Краткое объяснение и действие — пользователю, техническое исключение и ID операции — в диагностику, не в основной текст UI.

#### B. Непрерывный редактор
- Up/Down внутри визуальной строки обрабатывает TextBox; только достигнутая граница блока запускает переход. Событие boundary-navigation считается обработанным до первого await, чтобы нативная обработка не удалила символ и не передала фокус оболочке.
- Сохранять visual X при серии вертикальных переходов, clamp на короткой строке, возврат к прежнему X на следующей длинной. Учитывать soft-wrap, Ctrl+Enter, Unicode и разные типы блоков. Глобальный `+` не получает фокус от стрелок редактора.
- Left/Right на границе идут в соседний блок. Пустой завершающий блок используется только как реальная позиция добавления, а не вместо существующего соседа.
- Backspace при caret=0 и пустом selection объединяет совместимые текстовые блоки с предыдущим: paragraph, обычный heading без area marker, list/task-list item, blockquote. Тип предыдущего блока сохраняется; структурный префикс второго (`#`, list/check marker, `>`) снимается по действующим правилам, весь содержательный текст и внутренние переносы сохраняются. Caret ставится на стык. Первый блок — no-op; выделение удаляется обычным способом, а не объединяет блоки.
- При boundary merge с назначенным заголовком области, fenced code, таблицей или иным неподдержанным структурным блоком — handled no-op без удаления/смены focus и короткое объяснение «Эту границу нельзя объединить Backspace». Служебные area markers не удаляются и не становятся частью произвольного абзаца. Это явная защитная граница, а не обещание полной совместимости со всеми командами Obsidian; обычные заголовки/списки ею не ограничены. Добавить табличные tests совместимых/защищённых пар.
- Enter делит блок в caret, Ctrl+Enter вставляет перенос внутри блока. Текущая семантика Markdown сохраняется; undo split/merge возвращает текст и caret, не подменяется удалением одного символа.
- Правило Enter/Ctrl+Enter выше относится к обычным редактируемым текстовым блокам. Структурные исключения и точные fixtures:

| Пара/тип | Backspace на границе | Enter / Ctrl+Enter | Undo/инвариант |
| --- | --- | --- | --- |
| Paragraph A + paragraph B | `A` + `B` без разделителя блоков | Разделить в caret / внутренняя новая строка | Все символы и исходный caret восстановлены |
| Совместимые heading/list/task/quote без area marker | Снять structural prefix второго, оставить тип первого; `A` + `- [x] B` → `AB` | Существующая normal split/soft-line семантика с golden fixtures | Undo возвращает и снятый prefix/check state |
| Назначенный area heading с любой стороны | Handled no-op + объяснение | Enter создаёт paragraph после целого heading; Ctrl+Enter не разбивает однострочный заголовок и объясняет ограничение | Имя/HTML marker не дробятся и не дублируются |
| Fenced code / table / opaque block | Handled no-op + объяснение | Внутри raw-editable блока новая строка в его тексте, без принудительного top-level split | Parser/файловые данные не теряют fences/строки |

- Сохранить один клик, отсутствие рамки/скачков. Clipboard failure перехватывается на нужной границе вставки, сохраняет текст и фокус; не вводить глобальное подавление необработанных исключений.
- Handles видны при hover/selection; значок назначенной области остаётся видимым. Selection подсвечивает весь блок. Меню достижимо мышью и клавиатурой, удерживается при переходе указателя с блока на меню.

#### C. Разбор и конфликты
- После сохранения из редактора, capture, чекбокса, назначения области или DnD обновить связанный документ разбора и его ревизию, сохраняя идентичность выбранного диапазона.
- При гонке безопасен максимум один reload/retry: только когда прежний выбранный текст однозначно найден и не изменён, включая контекст областей. Изменённый, удалённый или неоднозначный диапазон не преобразовывать автоматически.
- При настоящем конфликте: «Запись изменилась. Проверьте выделение»; перечитать и дать выбрать диапазон заново. До решения пользовательский черновик не пропадает, задача повторно не создаётся.
- Предыдущий/следующий, изменение диапазона и области, существующий блок родителей, задача/цель, заметка, оставить, сегодня и пропустить сохраняются. Продвижение только после подтверждённого сохранения решения; ошибка оставляет текущий элемент.
- Индикатор прогресса показывает «Осталось N», а не создаёт впечатление возврата на шаг 1 после каждого решения.

#### D. Области, переносы и компактность
- «Сбросить фильтр» и «Все области» используют одно действие полного выбора, включая «Без области»; UI сразу пересчитывается. Пустой выбор имеет явное пустое состояние, не пустые дни.
- Единая иерархическая проекция областей используется в фильтре, capture и разборе. Сохранить существующую кратность выбора; дочерняя область отображается под родителем, путь отличает одинаковые имена.
- DnD одного/нескольких выделенных блоков сохраняет относительный порядок, переносит один раз, показывает точку вставки; drop на собственный диапазон — no-op. Keyboard move остаётся альтернативой.
- Если перенос меняет контекст области так, что блок скрывается фильтром, показать неблокирующее сообщение с «Отменить». Обратная операция доступна до следующей мутации этого документа/смены vault; не перетирает новые внешние изменения. Первое локальное изменение текста инвалидирует Undo немедленно, ещё до debounce/disk commit; один перевод caret/selection не инвалидирует. При устаревшей ревизии объяснить, почему отмена уже небезопасна. DnD → typing до debounce → Undo не должен потерять новый черновик.
- Hover-меню — компактный popover рядом с handle/выделенным диапазоном, clamped к viewport, не на дальнем правом краю окна. Частые действия: «Задача», «Заметка», «Область»; существующие списки/чекбоксы/выше/ниже доступны в «Ещё». Не добавлять постоянную полосу над каждым блоком.
- Сохранить текущую плотность и общую верхнюю панель; исправлять только подтверждённые лишние отступы/фокусные эффекты. Уведомление о разборе не перехватывает фокус при capture.

#### E. Поиск, файлы и формат даты
- При узком окне строка поиска занимает свою строку; фильтры переносятся или убираются в компактный «Период». Даты локализованы, все поля достижимы при 480 px; меню не выходит за viewport.
- Результат поиска показывает читаемый заголовок/фрагмент Markdown, путь/дату для различения и корректный переход к источнику; не выводит служебный task URL и разметку как основной текст результата.
- Перед применением формата даты считать M — файлы, распознанные старым форматом, N — сколько из них останутся распознаны новым. При N<M показать «В ленте останется N из M прежних ежедневных файлов. Остальные доступны в Файлах» с «Применить»/«Отмена». Дополнительно показать число вновь распознаваемых файлов, если оно ненулевое.
- Это read-only preview; не переименовывать файлы и не менять настройку до подтверждения. Отмена оставляет старую ленту/настройку. Пустая база и N=M не требуют лишнего подтверждения. Неполный/ошибочный scan не маскировать нулём.
- Во всех затронутых UI корректны accessibility name/state/help: soft-line hotkey, checked state, названия областей без технических record-строк, текстовые имена действий без зависимости от иконки.

## 7. Бизнес-правила / Алгоритмы
- Действие относится к vault/space, в котором начато; переключение пространства не переназначает его.
- Повтор одного operation ID даёт тот же destination, не ещё один append/task.
- Автоматическая замена разрешена только при доказанном соответствующем source range; одинаковый текст в нескольких местах не даёт права выбирать последний блок.
- Успех UI следует за фактом сохранения, а не за стартом команды. Recovery не зависит от существования review-session для capture.
- Undo использует ожидаемую revision; несовпадение не допускает blind overwrite.
- Фильтр отображает только дни с результатами; полный выбор включает «Без области».
- Изменение формата имён не изменяет файлов; подсчёт влияния использует одну и ту же naming-логику, что индексатор.

## 8. Точки интеграции и триггеры
- CaptureCommand/retry/recovery/restart → общий жизненный цикл operation ID.
- Editor save, checkbox, move, assign-area, note extraction/task conversion → update document projection + review revision + search invalidation.
- Space/vault reconfigure → отмена/отсечение устаревших UI callbacks и очистка transient Undo.
- Filter All/reset/parent-child toggle → одна синхронная selection projection.
- Resize/theme/font change → layout/hover clamp и доступные поля поиска без горизонтального обрезания.

## 9. Изменения модели данных / состояния
- Durable intent стадии append обязателен; переиспользовать существующее журналирование, расширяя persisted контракт версией/optional fields, с чтением старых записей. Не оставлять append-state только в памяти. Любой несовместимый enum/schema требует отдельной проверки совместимости, не считается автоматически безопасным.
- Поля impact preview, operation presentation state, preferred caret X и move Undo — вычисляемые/сеансовые, не новая пользовательская база.
- Любое новое persisted поле описать в журнале EXEC с compatibility fixtures; несовместимая миграция вне scope.

EXEC: `FeedTaskConversionRecord` дополнен optional `CaptureIntent` и `RecoveredCaptureWrite`; версия новых task-journals остаётся 2, отсутствующие поля читаются как `null`. `CaptureIntent` хранит `CaptureText`, `Area`, `InitialSourceRevision`, `AppendedTextHash`, `HasUtf8Bom`, optional `AppendedText` (доказательство полного результата append). `RecoveredCaptureWrite` хранит `RelativePath`, полный `Text`, `ExpectedRevision`, `HasUtf8Bom`, `CaptureText`, `Area`: это durable план повторного сохранения оставленного черновика, а не новая задача. Write intent сохраняется до изменения Markdown, затем фиксируется `ReviewApplied`. Путь исходного журнала и operation identity не меняются. Existing `FileJournalsEnumerateOnlyUnfinishedOperationsAfterRestart` проверяет schema1 enumeration; обычные schema2-конверсии без capture сохраняют прежний путь. Новые persisted payload/write plans проходят disk restart и forced process exit в `FeedCaptureProcessCrashTests`; это не гарантия forward compatibility старого бинарника, ограничение rollback ниже сохраняется.

## 10. Миграция / Rollout / Rollback
- Первый запуск читает существующий vault и pending-журналы, не переписывает заметки массово.
- Проверки выполняются на копиях/synthetic fixtures; приложение пользователя и его рабочая база не используются.
- Локальные изменения группировать по outcome; Git delivery отдельно. Откат кода — отдельно выбранные изменения после согласования, не hard reset. Данные не удаляются при откате; Markdown остаётся читаемым. Старый бинарник не обязан уметь продолжить новый intent: перед откатом незавершённые новые операции завершить либо безопасно оставить обе сущности в новой версии. Не запускать несовместимый recovery старым бинарником и не удалять journal для маскировки проблемы.
- Перед reconfigure ждать/фиксировать активные записи; не пересоздавать runtime поверх потерянного черновика.

## 11. Тестирование и критерии приёмки
- AC01: 10 повторных submit/retry одной capture-операции и fault injection до/после append/task/link/UI publish дают не более одного source capture-диапазона и одной задачи; чужие одинаковые блоки не заменены. Capture из нескольких абзацев, checklist и повторяющегося текста с trailing blanks целиком входит в одну задачу/замену; автоматически добавленный заголовок области остаётся. Реальный process-crash/restart после append ДО следующей journal-stage также не дублирует capture; отдельно проверить полночь и неоднозначный изменённый исходник.
- AC02: partial capture восстанавливается после restart без review-session, banner закрывается сразу после успеха; «Оставить как есть» сохраняет обе сущности; ошибки русские и actionable.
- AC03: стрелки работают по visual lines/между блоками, сохраняют X; Backspace merge не теряет содержательный текст, только нормализует структурный префикс по B; Enter/Ctrl+Enter/Undo корректны для LF/CRLF, soft-wrap, Unicode, пустых/коротких блоков и selection. Защищённые пары (area heading, fence, table) не меняют текст/markers/focus и объясняют no-op; обычные заголовки/списки объединяются.
- AC04: реальные click/type/paste не вызывают рамку, сдвиг или уход focus; инъекция clipboard failure не завершает приложение и не меняет текст.
- AC05: все решения разбора, диапазон, область, родители, задача/цель и note extraction работают; auto-advance только после commit; безопасный stale retry, неоднозначный/изменённый source защищён.
- AC06: All/reset/parent-child фильтры синхронны, включая без области; нет пустых дней; picker в capture/review отражает ту же иерархию.
- AC07: pointer DnD и клавиатурное перемещение 1/3 блока сохраняют порядок; self-drop no-op; исчезновение из фильтра объяснено; Undo безопасен при внешнем изменении и локальном typing до debounce.
- AC08: поиск заметки/задачи/старого daily-файла показывает readable result, корректно открывает источник; период/очистка/пустой результат доступны при 480/720/1139 px и увеличенном шрифте.
- AC09: impact N/M соответствует naming-скану; Cancel не меняет config/feed, Apply не меняет файлы; ошибки scan и невалидный формат безопасны; настройка переживает restart и изолирована по текущему контракту пространства.
- AC10: scroll fixture из 800 дней, включая один 200-строчный день, с несколькими scroll-страницами, фильтром и правкой при подгрузке не пропускает/дублирует дни, не теряет текст/focus/scroll anchor. Допустимая anchor-семантика при append снизу: текущий вертикальный offset относительно уже загруженного содержимого не меняется, а последний день прежней страницы остаётся материализованным в том же viewport. Editor controls ограничены viewport; полный индекс поиска/разбора может быть загружен независимо от скролла для согласованного масштаба 750–800 файлов. Существующие perf-tests не деградируют.
- AC11: два пространства с разными vault не смешивают notes/tasks/areas/config; поздний callback и pending recovery пространства A не появляются в B; внешняя правка выбранного/соседнего блока не перетирается.
- AC12: доступные имена/checked/help актуальны; hover-menu соответствует wireframe и не пропадает при наведении на себя; selection окрашивает блок; значок области сохраняется; напоминание скрывается и не ворует фокус, разбор доступен по меню/hotkey.
- AC13: обычная сборка и изолированная сборка test-host проходят; main/headless/FlaUI полные наборы заканчиваются green с ненулевым discovery и отчётами; долгие шаги логируют progress и завершаются управляемо.
- AC14: повторный ручной end-to-end проход всей фичи, включая успешную отдельную заметку/ссылку, родителей, перенос на сегодня, длинный scroll, multi-DnD, restart и внешние изменения; дефекты не маскируются компонентными тестами. При недоступности проверки итог incomplete, не «10/10».

### Команды и evidence workflow
В EXEC сначала прочитать skill `run-tunit-tests`, сверить SDK/global.json, repo scripts и discovery. Не запускать shared UI state параллельно.

```powershell
dotnet --info
dotnet build src/Unlimotion.sln --nologo
dotnet test --project src/Unlimotion.Test/Unlimotion.Test.csproj -c Debug --no-build --no-restore -- --treenode-filter "/*/*/FeedQuickTaskCaptureTests/*" --maximum-parallel-tests 1 --minimum-expected-tests 1 --output Detailed --report-trx
# Для full main/headless — текущий scripts/ci/Invoke-TestStage.ps1 с новым ResultsRoot
pwsh -File scripts/ci/Invoke-TestStage.ps1 -Stage test -Project main -ResultsRoot output/feed-reliability/full-run
pwsh -File scripts/ci/Invoke-TestStage.ps1 -Stage test -Project headless -ResultsRoot output/feed-reliability/full-run
dotnet test --project tests/Unlimotion.UiTests.FlaUI/Unlimotion.UiTests.FlaUI.csproj -c Debug --no-build --no-restore -- --maximum-parallel-tests 1 --minimum-expected-tests 1 --output Detailed --report-trx
git diff --check
```

Перед full run — build/restore всех тестовых модулей; остальные тестовые проекты решения определить discovery и также выполнить, если не охвачены этими тремя. Новый ResultsRoot для каждого запуска. Не повторять старый 15-минутный hang без логов и новой гипотезы. Expected red — только assertion дефекта, не ошибка сборки. Проход: reproducer → fix → targeted → обычная сборка → full → реальное окно → review. Время/память длинной ленты сравнить на одинаковой fixture/окне до и после; не заявлять performance без замера.

Обязательный preflight gate до каждого длинного запуска: записать в журнал отдельные лимиты discovery/bootstrap и test execution, обоснованные измерением/историей конкретного набора; передать MTP timeout или использовать поддерживаемый внешним runner deadline, а не безграничную команду. Указать progress-log, PID владельца и дочерних тестовых процессов. При отсутствии прогресса/timeout снять фазу, elapsed, CPU, последний шаг/stack при доступности и завершить только принадлежащее этому запуску дерево. Приложение пользователя не трогать. Затем исправить выявленную причину/сузить reproducer; полный gate всё равно обязателен. Запрещено скрывать CS0579 глобальным отключением генерации assembly attributes или исключением реальных source/tests.

## 12. Риски и edge cases
- Ошибка после disk write до UI publish: журнал и ownership важнее исключения команды.
- Повторяющийся одинаковый текст: нужен устойчивый locator, не поиск последнего совпадения.
- IME, surrogate pairs, CRLF и visual wrap: не выполнять boundary delete до вычисления целевой операции; проверять input composition.
- External edit между preview и commit: compare-and-swap revision, безопасный отказ без overwrite.
- Изменение области влияет на фильтр и очередь разбора; Undo не должно откатывать чужую последующую правку.
- Old pending journals без review-session и смена пространства: не смешивать completion markers.
- UI host внешней библиотеки может требовать исправления за пределами репозитория. Тогда остановить этот блок с evidence и запросить расширение, не подменять green отключением tests.

## 18. Альтернативы и компромиссы

- Новая универсальная система Undo: лишняя сложность; выбран ограниченный revision-safe inverse последнего переноса и локальный editor undo.
