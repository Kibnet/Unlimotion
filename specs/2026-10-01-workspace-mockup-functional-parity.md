# Функциональное сближение рабочего пространства с интерактивным макетом

Expanded SPEC: QUEST-профили `product-system-design`, `ui-feature-parity`, `ui-automation-testing`, `.NET desktop UI`.

## 0. Метаданные

- Тип: UX-функция существующего Avalonia-приложения.
- Владелец: пользователь — outcome и утверждение; агент — детализация и проверка.
- Масштаб: large: навигация, разбор, заметки, карточка задачи и адаптивный shell.

- Поверхность: нативный Unlimotion, общий `MainScreen` на поддерживаемых размерах окна.
- Effective runtime: не применимо — не меняется модель ИИ.

- Ограничения: не терять текст/вкладки, не редактировать пользовательскую базу для проверки, не менять Markdown/task schema без отдельного решения.

## 1. Overview / Цель

- Исходное поручение: сравнить текущую реализацию с первоначальным интерактивным макетом и устранить **функциональные** разрывы.
- Success means: пользователь может пройти основные сценарии макета в реальном приложении без потери контекста, лишних обходных шагов или данных, сохранив утверждённые позднее правила навигации.
- Output: нативный UI, локализация, целевые Headless/FlaUI проверки и визуальные свидетельства до/после.
- Stop rules: до точной фразы «Спеку подтверждаю» не менять код; в EXEC остановить переход при неуспешном commit редактора, конфликте источника или непроверенной миграции данных.

## 2. Текущее состояние (AS-IS) и сравнительный аудит

| Сценарий макета | Текущая реализация | Решение |
| --- | --- | --- |
| Лента и задача рядом; две заметки рядом | Работают через `WorkspaceNavigationViewModel` и две панели, проверены UX-сценариями | Сохранить и регрессировать |
| Общие `+`, поиск, настройки, task-space и история | В shell есть; быстрый захват поддерживает task checkbox, область и родителя | Сохранить; не дублировать в панелях |
| Разбор с видимой исходной записью слева и действиями справа | `FeedReviewDialog` — app-wide overlay поверх затемнённой ленты | **Разрыв R1:** открыть разбор в workspace-панели рядом с исходным блоком |
| Переместить активную вкладку в другую панель; объединить панели | Меню `WorkspacePaneView` даёт «Открыть рядом» для другой цели и «Закрыть панель»; последнее очищает вкладки secondary | **Разрыв R2:** move/merge с сохранением вкладок и текста |
| Общий раздел «Заметки», закреплённые заметки | «Файлы» доступны только из ленты; постоянного входа/закрепления нет | **Разрыв R3:** доступный из shell браузер заметок и явное закрепление |
| «К исходной записи» в задаче, созданной из ленты | Conversion journal знает исходный файл/блок, но карточка не предлагает переход | **Разрыв R4:** обратная ссылка через надёжное происхождение |
| «Добавить следующий шаг» на карточке | Можно создать задачу через `+` и назначить родителя вручную | **Разрыв R5:** действие от карточки с предзаданным родителем |
| Узкий экран с понятным переключением контекста | Работает, но подписи «Основная/Рядом», много уровней верхней панели; источник текущего объекта неясен | **Разрыв R6:** контекстные подписи и компактный overflow без скрытия основных команд |
| Открытые заметки как документы | Workspace tab уже есть, но внутри Feed-документа остаётся отдельный заголовок с путём и `×` | **Разрыв R7:** одна понятная точка закрытия, путь — tooltip/меню |

Инвариантные расхождения с макетом: в макете история живёт в каждой вкладке и можно получить несколько экземпляров объекта; позднее пользователь утвердил **общую историю** и **один открытый экземпляр**. Эти механизмы не возвращать. Демонстрационные дата, содержимое и сценарные кнопки в HTML не являются требованиями к данным приложения. Визуальная тема/точные пиксели макета — ориентир и отдельный visual check, не функциональный контракт.

Код: `MainScreen.axaml(.cs)` владеет shell/overlay; `WorkspacePaneView.cs` — вкладками/меню; `WorkspaceNavigationViewModel.cs` — open/close/history; `FeedControl.axaml` — Feed/документ; `FeedViewModel` и conversion journal — разбор и происхождение задачи; `SettingsViewModel` и task-source note profile — настройки базы. Реальные зависимости и поля перепроверить в EXEC до изменения.

## 3. Проблема

Единая оболочка уже показывает объекты рядом, но важные действия по-прежнему привязаны к старым модальным/вложенным поверхностям. Пользователь теряет исходный контекст разбора, не может безопасно перекомпоновать панели и вынужден совершать обходные переходы между заметкой и задачей.

## 4. Цели дизайна

- Один видимый источник истины для маршрута/закрытия документа; один объект — одна открытая вкладка.
- Разбор как работа с источником, а не модальный отрыв от него.
- Операции с панелями сохраняют вкладки, редакторское состояние и общую историю.
- Прямые, но необязательные связи «задача ↔ исходная запись» и «задача → следующий шаг».
- Команды остаются достижимыми с мыши, клавиатуры и touch; широкое/узкое окно используют одинаковую модель.

## 5. Non-Goals

- Не возвращать per-tab history/дубликаты открытого объекта, не копировать демонстрационные данные макета.
- Не менять формат ежедневных `.md`, состояние задач, правила разбора, области, сроки или статусы.
- Не вводить новый общий граф ссылок и не сканировать все заметки на каждом рендере карточки.
- Не заменять docking-библиотеку, не проектировать произвольное число панелей или сохранение полной компоновки после перезапуска.
- Не исправлять несвязанные CLI/task-manager изменения, уже присутствующие в рабочем дереве.

## 6. Предлагаемое решение (TO-BE)

### 6.1 Распределение ответственности

| Компонент | Ответственность |
| --- | --- |
| `WorkspaceNavigationViewModel` | Тип маршрута «Разбор», move/merge/close, unique object key, commit gate, история/активная панель. |
| `MainScreen` / `WorkspacePaneView` | Общие команды, контекстное меню вкладок/панелей, адаптивные подписи и overflow; UI не меняет модель в обход координатора. |
| Feed review view/model | Текущая очередь и решения, локатор исходного дня/блока, подсветка, next/previous/confirm/undo; бизнес-логику не копировать в shell. |
| Note browser / pins | Общий из shell вход в существующий список файлов; закреплённые ссылки как UI-навигация, не изменение `.md`. |
| Task card / conversion provenance | Обратный переход к источнику и запуск существующего создания задачи с предзаданным родителем. |
| Localized resources / UI tests | Все новые надписи, automation IDs, сценарии/скриншоты и негативные проверки. |

### 6.2 Детальный дизайн

**R1 — разбор рядом с источником.** Кнопка/сочетание «Разбор» открывают единственный маршрут разбора, а исходную ленту с текущим блоком показывают в другой панели. Если лента или разбор уже открыты — активировать их вкладки; не создавать копий. При открытых двух панелях не закрывать/не заменять чужие вкладки: добавить/активировать соответствующие вкладки в существующих панелях после commit; явно выбранная пользователем вкладка остаётся в strip. На узком экране открыта панель решения; кнопка «К записи» переключает на исходный блок, «К разбору» возвращает. После подтверждения подсветка/локатор переходят к следующему блоку в установленном порядке; без решения кнопки next/previous лишь меняют фокус. Завершение/закрытие разбора оставляет ленту и прочие вкладки. При отсутствии базы, блоков или ошибке сохранения — видимое empty/error состояние, без полуперехода и потери черновика. Использовать существующий `FeedReviewDialog` как встраиваемое содержимое либо выделить из него единый view; не иметь двух конкурирующих review sessions.

**R2 — move/merge.** Меню активной вкладки: «Переместить в другую панель»; меню панели: «Объединить панели» (secondary → primary). Move сохраняет tab ID, текущий маршрут/позицию/черновик и историю, не клонирует объект; если исходная панель опустела, вернуть безопасную корневую вкладку или убрать пустую secondary. Merge переносит все вкладки в стабильном порядке, без потери неактивных, сохраняет активную вкладку и unique-key invariant; повторный ключ активируется один раз, но его незаписанный state/commit должен быть обработан до удаления. `Close pane` остаётся отдельной явно разрушительной операцией, подписанной «Закрыть панель и её вкладки» с количеством вкладок при >1; commit failure отменяет всю операцию. И move, и merge имеют доступную клавиатурой/touch команду меню. История после операции адресует перенесённые tab IDs; Back не возрождает дубликат.

**R3 — заметки.** В общем rail/его overflow появляется «Заметки», открывающее существующий браузер файлов в текущем контексте, не требуя переключиться в ленту. На узком экране пункт доступен из общего меню. Открытие результата использует стандартные «здесь/новая вкладка/рядом» и unique-key правила. В меню открытой заметки — «Закрепить/Открепить»; в rail видны закреплённые названия, на узком — в общем меню. Порядок закрепления — добавления; повторы/несуществующие пути не показывать как живые документы (показывать недоступный пункт с удалением из закрепления). Список закреплений хранить в настройках **по идентичности базы/пространства**, нормализованный относительный путь без абсолютного пути; путь не меняет Markdown. При смене базы не показывать чужие закрепления; при первой загрузке список пустой. Одноимённые файлы различать папкой в tooltip/второй строке меню. Если существующий file browser нельзя встроить как маршрут без нарушения модели, открыть его как общую панель поверх workspace, но сохранить исходную вкладку и точно тот же выбор результата; выбор в EXEC зафиксировать по фактической архитектуре.

**R4 — исходная запись.** В карточке задачи, созданной из Feed, показывать «К исходной записи» с датой/коротким местом; действие открывает vault+relative path+block locator стандартным workspace переходом и подсвечивает блок. Источник определить по уже записанной conversion provenance/journal; для новых записей при необходимости добавить отдельный локальный индекс task-source→note-source, не изменяя task schema/пользовательский Markdown. Поиск — ленивый, индексированный/ограниченный текущим vault/task source, не полный обход 3-летней базы при каждой карточке. Для старых задач без достоверного источника ссылку не показывать; для нескольких подтверждённых источников — список выбора. Удалённый/переименованный файл — понятная ошибка и возможность оставить задачу; чужое пространство не открывать молча. После перезапуска переход должен работать для записей с сохранённой provenance.

**R5 — следующий шаг.** В карточке задачи команда «Добавить следующий шаг» вызывает существующий диалог создания задачи с текущей задачей как предвыбранным родителем (не заменяя остальные parent relations и area defaults). Пользователь видит родителя до сохранения и может изменить; пустое имя/ошибка записи не создают задачу. После создания новый шаг открыт/доступен по общим правилам навигации, исходная задача доступна через Back, но автоматическая смена статуса родителя не производится.

**R6/R7 — компактность и одно действие закрытия.** На узком окне pane switcher показывает тип/короткое имя активного объекта каждой панели («Лента», «Разбор», название заметки/задачи) и текущую панель; длинные имена усекать с tooltip. Общие поиск, `+`, история и меню остаются достижимы, не наезжают друг на друга; скрытые команды переходят в overflow, не исчезают. Для отдельного Feed-документа убрать внутреннюю кнопку `×` и дублирующий крупный path/title header; в workspace tab оставить название и закрытие, полный путь в tooltip/меню. Сам текст/заголовок Markdown и breadcrumb, необходимый для ориентации, не удалять. Не менять редакторскую разметку или высоту блока при фокусе.

Visual plan (функциональная структура, не пиксельная копия):

```text
Широкое окно
┌ +  Пространство  Поиск  ← → История  Настройки ⋯ ┐
├ Лента / Задачи / Заметки / Разбор / Закреплено ──┤
│ [Лента ×] [Заметка ×] │ [Разбор ×] [Задача ×]    │
│ день + выделенный блок│ решение + prev/next     │
│                      │ область/родитель/OK     │
└──────────────────────┴───────────────────────────┘
Узкое окно: общая компактная панель → [Лента: дата] [Разбор: блок] → одна панель.
```

Visual reference: локальный HTML не является версионируемым контрактом; сохранить в EXEC сопоставимые screenshot/video artifacts с названием сцены, шириной и состоянием. Если HTML недоступен — пользоваться описанием/wireframe и зафиксированными baseline screenshots, не выдавать это за pixel-parity.

### 6.4 State / Interaction Matrix

| Состояние | Триггер | Переход | Пустое/ошибка/конкуренция |
| --- | --- | --- | --- |
| Две занятые панели | Разбор | Добавить/активировать Feed и Review без сброса остальных | commit отказал → исходная компоновка и черновик |
| Review на узком | «К записи»/confirm | Переключить панель/обновить локатор | нет следующего → состояние «Всё разобрано» |
| Secondary с несколькими tabs | Merge | Перенести все, закрыть только пустую secondary | конфликт записи → операция целиком отменена |
| Активная вкладка | Move | tab ID/route остаются, меняется pane | повторный ключ → активировать существующий, не клонировать |
| Другая база/пространство | Открыть pin/source | Только текущий scoped список | отсутствует/чужой → ошибка/недоступно, нет silent fallback |
| Задача без provenance | Просмотр карточки | Нет обещающей ложной ссылки | старый журнал/удалённый файл → сообщение, задача остаётся |
| Последняя вкладка | Закрыть/перенести | Без пустой workspace-панели | fallback root по существующему правилу |

## 7. Бизнес-правила / Алгоритмы

- `ObjectKey` остаётся уникальным среди текущих вкладок всего workspace; Review имеет один ключ на scope, Notes browser — один ключ/одна общая панель.
- Merge/close проходят двухфазно: проверить commit каждой затронутой вкладки, затем атомарно изменить коллекции. Никакого частичного переноса.
- Для источника задачи идентичность включает task source и vault; путь нормализуется как vault-relative, вне vault отклоняется. Если точный block locator устарел, открыть документ с предупреждением, не выделять произвольный текст.
- Pin не создаёт документ и не влияет на редактор; изменение pin атомарно сохраняет конфигурацию, при сбое UI откатывает toggle/показывает ошибку.
- Review порядок и решения остаются из существующей логики, без нового алгоритма отбора.

## 8. Точки интеграции и триггеры

- Общие Review button/menu/hotkey → координатор → Feed review VM + source locator.
- Tab/pane context menu → move/merge/close coordinator; header narrow labels подписаны на активные маршруты.
- Shell Notes/pins → существующий file browser → workspace open; tab menu → pin store.
- Task card load → lazy provenance lookup; source action → workspace open; quick-child action → existing create task flow.
- Scope change (task space/vault) → перечитать pins/provenance, не смешивать панели из разных scope по прежнему workspace контракту.

## 9. Изменения модели данных / состояния

- Persisted: только конфигурация закреплённых relative paths по scope; если journal нельзя читать как lookup, отдельный локальный индекс provenance для **новых** конверсий с версией/восстановлением из journal. Точный storage type выбрать в EXEC после inspection, не менять пользовательские task/Markdown файлы.
- Calculated: review route/source locator, contextual pane title, lazy task-source link.
- Runtime: move/merge меняют pane membership существующих tab IDs; история остаётся общей, не сохраняется между запусками.

## 10. Миграция / Rollout / Rollback

- Первый запуск: пустой список pins; текущие вкладки/данные читаются как прежде. Старые tasks без однозначного provenance остаются без backlink.
- Откат к предыдущей сборке игнорирует новые аддитивные настройки; task/Markdown storage не меняется. При несостоятельном индексе provenance можно удалить/пересоздать только этот индекс, не user data.
- UI review fallback при невозможности встроить в панель должен сохранять текущий modal без деградации, но AC1 тогда не закрыт: нельзя объявлять работу выполненной.

## 11. Тестирование и критерии приёмки

AC1. Review из любой вкладки показывает исходную запись и decision view в двух панелях; при confirm/next/previous/undo синхронно меняет локатор/подсветку, остальные tabs не исчезают; narrow «К записи» работает; ошибки commit не меняют workspace.

AC2. Move активной вкладки и merge сохраняют все tabs/черновики/tab IDs/общую Back/Forward историю. Отдельное закрытие панели ясно названо и не закрывает ничего при commit failure.

AC3. Notes доступны из задач без промежуточного Feed; pin/unpin доступно из меню, сохраняется после перезапуска в своей базе, не смешивается между базами, missing file объясним.

AC4. Карточка feed-created task открывает точную исходную запись после перезапуска; Back возвращает; без provenance/при missing/scope mismatch нет ложного перехода.

AC5. Следующий шаг создаётся из карточки с видимым предвыбранным родителем; изменение родителя и cancel работают, запись создаёт связь без смены статуса родителя.

AC6. При 390, 520, 1000 и 1400 DIP общие команды и pane switcher не перекрываются; подписи называют активные объекты и доступны в tooltip/automation name. Клавиатурное меню и touch-путь покрыты.

AC7. Открытый отдельный Feed-документ имеет один видимый close в workspace tab; его заголовок Markdown/контент/scroll не меняются, полный путь доступен.

## 12. Риски и edge cases

- Самый высокий риск — конкурирующие review overlay и route, а также shared selection в двух панелях. Единый coordinator/session и тесты переходов обязательны.
- Move/merge с несохранённым Markdown/ошибкой записи могут потерять данные: двухфазный commit gate и негативный UI-тест.
- Долгий поиск происхождения по трёхлетней базе: lazy indexed lookup, ограниченный source/vault, без линейного обхода при каждом render.
- Неоднозначная/удалённая заметка, разные базы, переименование пути, stale locator: без автоматического выбора чужого файла.
- На 390 DIP пункты меню и название могут не поместиться: overflow, clipping и automation names.
