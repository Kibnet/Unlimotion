# Unlimotion CLI

Помогай пользователю работать с задачами в локальном файловом пространстве Unlimotion через актуальный CLI. Проверенный контракт — `main` на `d1e6702f` / `v1.32.0`. Считай фактически запущенный бинарник и его JSON-вывод источником истины: версия репозитория, старый отчёт и название карточки не подтверждают текущую установку или состояние задач.

## Перед командой

- На Windows разреши `Get-Command unlimotion-cli` до абсолютного пути исполняемого файла и закрепи его для всей связанной серии (например, `$cliExe = (Get-Command unlimotion-cli -CommandType Application).Source`; далее `& $cliExe ...` для version/help/context, поиска, чтения, preview, записи, inspect и read-back). Если путь — неоднозначный alias/wrapper или обнаруженная команда сменилась, остановись перед записью. Не смешивай вывод одного бинарника с командой из другого `PATH`/checkout.
- У того же бинарника проверь `version --format json` и JSON `help` нужных команд. Скилл использует `context`, `search`, `task --include`, `apply schema/example` и `apply inspect`. Удостоверься, что `packageVersion` соответствует разрешённому пути: `dotnet tool list --global` подходит только для global shim, для `--tool-path` нужен соответствующий `dotnet tool list --tool-path`; у local build учитывай `buildKind=local`. Если актуальный контракт отсутствует, остановись до изменения задач и предложи отдельно обновить CLI; не переходи на старые команды и не обновляй инструмент автоматически. Для неизвестной более новой версии проверь справку/схему и соответствующие исходники; при неясной семантике не выполняй мутацию.
- Выбери task-space через `context [--tasks <путь пользователя>] --format json` того же бинарника. Приоритет: явный непустой `--tasks` → непустой `UNLIMOTION_TASKS` → active desktop settings; ошибочный выбранный путь не вызывает тихий fallback. Если пользователь указал каталог, передай его в `context` сразу. Возьми абсолютный `tasksPath` и передавай его как явный `--tasks` **во все** связанные вызовы. `context` проверяет существование каталога, но не граф и не будущую возможность записи.
- Предпочитай `--format json`. Для чтения используй `status`, `unlocked`, `candidates --limit <1..100>`, `task --include`, `validate`; `search` ищет ID/title по всем статусам, включая NotReady, Completed и Archived. Передавай неизменные фильтры и закреплённый `--tasks` при переходе по `nextCursor` до `null`; страницы не являются единым snapshot, поэтому дедуплицируй ID и при необходимости повтори поиск. `claim` не нужен для просмотра. Для изменения существующей задачи сначала проверь ID чтением в выбранном пространстве.

## Изменение задачи

Выполняй только изменение, которое пользователь поручил для конкретной задачи или набора задач. После конкретного согласия не запрашивай его повторно. Статус `Completed` не выводи из возраста задачи, checkbox, PR, готовности дочерних карточек или косвенного внешнего результата.

1. Прочитай исходную задачу через `task --id <id> --include details,relations,criteria,history,execution --format json` и нужные связанные задачи. Зафиксируй поля, которые должны сохраниться.
2. Для обычного изменения выбери наиболее узкую доступную CLI-команду. Для редактирования описания, дат, связей или нескольких полей используй `apply` с подтверждённым контрактом запущенной версии. Возьми синтаксис из `apply schema --format json`, шаблон из `apply example ... --format json` и семантические ограничения из `help apply`; замени примерные ID/ETag. Схема проверяет форму, не бизнес-правила. Для операции `setStatus` с терминальным статусом проверь требования к `justification` и абсолютным `evidenceLinks`; не выдумывай доказательства завершения. При риске потерять сгенерированный ID предпочти request для `apply` с операцией `createTask`, заранее выбранным `newTaskId` и preview.
3. Для `apply` сначала выполни `--dry-run`, проверь `success`, `changedTaskIds`, `operationResults` и `didMutate=false`. Если preview отклонён, не запускай запись. После успешного preview отправь тот же request один раз. Перед любой иной мутацией также проверь актуальное состояние и бизнес-правила команды.
4. После успешного ответа прочитай через тот же CLI и `--tasks` все `changedTaskIds`/`createdTaskIds`, а не только исходную задачу. Сверь изменённые поля и явно сохраняемые статус, даты, длительность, критерии и связи; `task --include details` также показывает `repeater`. Отдельно отмечай допустимые производные изменения, например timestamp или доступность родителя. Не называй операцию завершённой по одному exit code.

При `outcomeUnknown`, timeout после отправки мутации или потерянном выводе не повторяй команду вслепую: дождись освобождения `.unlimotion.lock`, прочитай авторитетное состояние через CLI и установи исход. Lock не удаляй. Для `apply` вызови `apply inspect --request <тот же файл> --tasks <закреплённый путь> --format json`: `receiptMatched` подтверждает receipt для точного request hash, но не сохранность текущего состояния; `desiredStatePresent` — только текущее состояние, не история; `readyForPreview` допускает новую проверку, но не доказывает неуспех прежней записи; `needsReconciliation`/`reconciliationRequired` требуют сверки, не повтора. Отдельно читай затронутые ID. Не меняй декодированный текст request между записью и inspect: пробелы и переносы входят в hash. `inspect` не отправляет новую application mutation, но доступ к storage может восстановить ранее незавершённый журнал. При потере ID обычного `create` отсутствие результата в ограниченной выборке не доказывает отсутствие записи; без однозначного read-back остановись с исходом «неизвестен». Не читай файлы задач напрямую и не повторяй `create`. При `validationFailed` на посторонней задаче не исправляй её и не обходи CLI прямым редактированием JSON. Для отказа из-за ETag, статуса или lease перечитай задачу и пересмотри действие в исходном пользовательском scope.

## Выполнение агентом

Для agent execution используй `candidates` → `task --include details,relations,criteria,history,execution` → `claim` только когда поручено взять задачу. `claim` переводит `Prepared` в `InProgress` и возвращает `leaseId`. Дальше `execution question`, `answer`, `result`, `complete` и `release` требуют точную пару `agentId + leaseId`; не угадывай чужой lease. `execution result` сохраняет промежуточный итог, `execution complete` проверяет критерии и завершает задачу. Обычный `complete` не завершает задачу с активным execution. При `leaseMismatch` используй `authoritativeTask` и свежее чтение, не повторяй команду со старым lease.

## Ответ пользователю

Для чтения назови task-space/source, IDs и наблюдённые факты. Для изменения назови ID, порученное действие, результат read-back и то, что осталось неподтверждённым. Разделяй выполненную мутацию задачи и реальное выполнение работы по ней. Если CLI отказал, передай точный error kind/message и безопасный следующий шаг.
